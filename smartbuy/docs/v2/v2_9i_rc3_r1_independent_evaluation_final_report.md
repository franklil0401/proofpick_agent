## 1. 最重要的反例：610毫米上限丢失

冻结任务：`rc3i-monitor-011`。

> 请从已收录的显示器中挑选：刷新率至少144Hz，机身宽度最多610毫米。不限制地区，保持各配置独立，给出符合条件的选择及依据。

冻结数据和独立只读SQL给出的结果：

| 商品 | 刷新率 | 宽度 | 是否满足两项要求 |
|---|---:|---:|---|
| ASUS PG27AQDM CN | 240Hz | 605mm | 是 |
| LG 27GS95QE-B CN | 240Hz | 604.4mm | 是 |
| BenQ EX2710U CN | 144Hz | 609mm | 是 |
| Dell G2724D CN | 165Hz | 611.9mm | **否，超过610mm** |

系统最后却推荐了上述四款，包括Dell G2724D。

### 实际发生了什么

1. 用户明确提出刷新率和宽度两个硬约束。
2. LLM的任务摘要和SQL建议都识别到了宽度≤610mm。
3. 默认显示器链路的确定性解析器没有识别中文单位“毫米”；最终ConstraintSet只保留刷新率≥144Hz。
4. 工具适配层根据这个不完整的ConstraintSet重建SQL过滤条件，宽度条件被丢掉。
5. Evidence Check与最终Checker只核验了刷新率，Dell G2724D因此成为eligible并进入最终推荐。

**Checker没有被绕过，数值比较本身也没有算错；它根本没收到用户的宽度要求。** “输出是Checker合规集合的子集”并不能证明“输出满足用户完整需求”。

只读定位：

- `smartbuy/constraints/normalize.py:342`：宽度正则支持mm/cm，未匹配本题“毫米”。
- `smartbuy/agent/react.py:850`：另一处宽度解析也匹配mm。
- `smartbuy/agent/react.py:628`：按确定性ConstraintSet重建过滤条件。
- `smartbuy/tools/text2sql.py:232`：正式执行确定性模板，而非直接执行展示的LLM SQL。
- `smartbuy/api/router.py:494`：统一产品入口的Monitor仍走V1兼容编排器。

本轮用原始响应、冻结数据和只读Parser/SQL再次核实，未重新调用模型，未修改代码。机器证据见[产品失败审计](../../eval/v2_9i_independent/results/product_failure_audit.json)。

## 2. 另一个可用性问题：精确型号仍被要求澄清

任务001、005、007均属于明确身份的双字段事实查询。用户已经给出型号、地区及精确配置标识，系统仍因共享系列词被判为歧义，未调用工具、未返回已知事实。

例如：

> UltraSharp U2723QE（CN地区；配置标识 dell-u2723qe-cn）的机身宽度和分辨率各是什么？

冻结数据中有611.4mm和3840×2160，但系统要求用户继续明确配置、地区或数值阈值。

`smartbuy/agent/react.py:880`的预检按单独英文token匹配产品名称；UltraSharp匹配多个产品时即拒绝，未使用同句中精确的U2723QE/product_id解除歧义。类似情况也出现在ProArt共享系列词。

这是“误澄清/错误空回答”，不应归为未知数据或安全拒答成功。

## 4. 我方评测器事故与获授权修订

必须同时披露这段历史，不能只保留后来更好看的分数。

- 初始评测器在第2题误报Evidence绑定错误并暂停。
- 原因一：V1接口将SQLite JSON TEXT作为引用值返回，例如字符串`"60.0"`，而金标为数值60.0。
- 原因二：仅含ID/字段/来源、`value=null`的引用被误判为矛盾事实断言。
- 人工审计确认第2题实际正确回答60Hz和27英寸，引用身份与来源也正确；**这不是产品安全失败**。
- 用户明确授权后，新增`score_v2.py`兼容层；原评分器、错误输出和原始响应未改。
- 兼容层只做严格JSON类型转换与“仅引用/数值断言”区分，不接受模糊单位字符串、不放宽错误身份或错误数值。
- 新增8项测试，加原9项合成测试，17/17通过。
- 修订冻结并推送提交：`d43d6b1`，之后才执行剩余任务。
- 前两题只使用保存的原始响应重新审计，没有再次调用API。
- 第11题是修订后独立复核确认的真实产品约束违规，不是上述误报的延续。

记录分别见[初始事故审计](../../eval/v2_9i_independent/results/harness_incident_audit.json)、[修订冻结](../../eval/v2_9i_independent/adapter_revision_freeze.json)、[修订评分结果](../../eval/v2_9i_independent/results/trusted_scores_v2.json)。

## 6. 给开发Agent的修改建议

建议只开一个有边界的修复轮次，先解决实际产品入口，而不是继续换搜索Provider或扩展品类。

1. **统一入口契约。** 审计UI、Portfolio API、CLI评测是否真正共享同一意图、身份和约束解析路径。不要在内部评测使用新版解析器，却让默认显示器UI继续依赖旧正则。
2. **补齐单位规范化。** 在通用字段/单位契约中处理毫米/mm、厘米/cm等合法表达；不要补丁式识别本题句子、型号或case ID。
3. **增加需求覆盖门禁。** 用户明确提出但尚未完成可靠绑定的硬要求不能默默丢弃。即使LLM建议因来源验证未通过而被拒绝，也应保留“未解决的用户要求”，澄清或安全停止，不能以剩余条件继续宣称全部满足。
4. **修正身份解析优先级。** 精确product_id/配置/地区命中优先于共有系列词，覆盖“系列全称+精确型号+地区”的通用组合。
5. **对实际API做回归。** 增加中文/英文单位等价、双条件单条件遗漏、全称/简称/配置号等价、完整条件集合直到Checker的闭包测试，优先使用虚构商品测试泛化。
6. **保护冻结与评测隔离。** 不改RC3、main、V1 Tag或本轮题目/原始结果；独立修复分支提交通用修复。修复后已运行11条只能是exposed regression，不能再称未见题。
7. 剩余79条虽然未调用，但若开发方接触了其题目或金标，也不能自动当作未见Holdout。不要让开发Agent预览后续测试文件；独立发布方案应重新确认隔离状态。

**不建议为通过这次测试放宽Checker，也不建议切换模型后反复重跑同一道题。** 当前反例表明问题位于确定性输入合同和真实入口的一致性，模型在本次已经理解了宽度条件。

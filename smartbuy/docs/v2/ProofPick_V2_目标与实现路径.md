## 2. 技术结论

ProofPick V2 的目标不是把所有市售电子产品预先写入一个静态知识库，而是建立一套：

> **以本地可信数据保证稳定性，以受控联网研究扩大商品覆盖，以有界 Agent 完成工具编排，以字段级证据和确定性 Checker 保证推荐边界的多品类电子产品决策平台。**

最终系统必须同时解决四个问题：

1. **已有商品如何可靠决策：** 使用治理后的结构化数据和产品资料完成可复现筛选与核验。
2. **新商品如何及时覆盖：** 数据库中没有目标型号时，Agent 能主动搜索网络并形成带来源的研究结果。
3. **动态信息如何处理：** 当前价格、库存、在售状态和近期变化必须来自带观察时间的动态来源。
4. **如何避免搜索结果误导推荐：** 搜索摘要和模型总结不能直接成为商品事实，必须经过网页提取、字段规范化、证据核验和 Checker。

因此，V2 不是“仍然只查已有文档”，也不是“所有问题都上网搜索”。正确形态是：

| 数据路径 | 使用场景 | 输出权限 |
|---|---|---|
| 本地可信路径 | 已治理商品、稳定规格、硬约束筛选、离线评测 | 可进入确定性推荐 |
| 受控联网路径 | 新型号、当前价格、库存、缺失字段、过期信息、来源冲突 | 先进入临时证据，核验后才能影响结论 |

## 3. “面向所有电子产品”的工程定义

“所有电子产品”不能解释为一次性覆盖市场全部 SKU。V2 对通用性的可验收定义是：

### 3.1 新增商品不修改业务代码

新增商品通过 Product Pack 导入，系统自动完成格式和单位校验、型号与地区版对齐、字段级来源记录、SQLite/事实卡/向量索引构建、数据发布和失败回滚。

首个验收案例是：不修改 Python 业务代码，导入第 13 个显示器，并能被 SQL、KB、Evidence Check 和 Checker 使用。

### 3.2 新增品类不修改通用内核

新增品类通过 Domain Pack 描述字段、单位、别名、约束、来源规则、评分维度和 Checker 规则。通用 Agent Runtime 不直接理解“刷新率”“处理器”“降噪”等品类字段。

### 3.3 未治理商品仍可研究

本地不存在的型号进入开放研究模式。Agent 可以搜索、打开网页、提取字段和生成研究报告，但必须标记为“开放研究”，不能伪装成完整治理数据上的确定性推荐。

### 3.4 用三个差异品类证明通用性

- 显示器：稳定规格和接口约束明显。
- 笔记本电脑：配置版、性能、续航和便携存在复杂权衡。
- 耳机：主观体验、连接兼容和动态使用场景占比更高。

只有三个品类共用同一内核、工具协议、证据模型和评测框架，才能证明项目不是多个固定 Demo 的拼接。

## 4. 两种工作模式

### 4.1 可信决策模式（Trusted Decision Mode）

适用于已安装 Domain Pack、商品数据已治理、Checker 规则完整的品类。

系统必须：

- 区分硬约束、软偏好、使用场景、上下文条件和待澄清项。
- 使用 Product Query/Text2SQL 生成完整候选池。
- 使用 KB Search 和 Reranker 核验稳定规格。
- 在证据缺失、冲突或过期时按需调用联网工具。
- 让每条关键事实绑定型号、字段、来源、地区、版本和时间。
- 在输出前由独立 Checker 复核全部硬约束。
- 输出推荐、排序理由、淘汰原因、冲突、未知字段和降级状态。

关键字段未知、证据冲突未解决或 Checker 异常时必须 fail closed。

### 4.2 开放研究模式（Open Research Mode）

适用于本地没有商品、品类尚未完整治理或用户询问最新市场信息的情况。

系统可以搜索官方网站、官方支持页、可信零售页和专业测评，提取字段级证据，比较来源、地区、版本和时间，并生成研究摘要、临时候选和待核验清单。

系统不得：

- 把搜索摘要直接当成商品事实。
- 把开放研究候选标记为已通过完整治理。
- 在价格缺少地区或观察时间时宣称“当前最低价”。
- 用论坛、评论或模型常识覆盖官方稳定规格。
- 自动登录账户、绕过验证码、下单或执行支付。

两种模式必须在 API、UI、工具轨迹和最终报告中明确区分。

## 5. 联网搜索的定位与触发规则

### 5.1 必须联网的情况

- 用户询问当前价格、库存、促销或在售状态。
- 用户询问本地数据库中不存在的新型号。
- 本地证据缺少影响决策的关键字段。
- 本地来源对同一字段存在冲突，需要核对版本或地区。
- 用户明确要求“最新”“现在”“近期发布”。
- 需要确认固件更新、兼容性变化或产品停售信息。

### 5.2 默认不联网的情况

- 本地已有充分官方证据的稳定规格问答。
- 对治理商品执行预算、尺寸、接口等结构化筛选。
- 已有证据足够完成的固定商品比较。
- 离线回归、消融实验和无网络 Demo。

### 5.3 联网前置判断

Agent 在调用联网工具前必须记录原因：

- `dynamic_fact_required`
- `unknown_product`
- `critical_field_missing`
- `evidence_conflict`
- `evidence_stale`
- `user_forced_latest`

不满足上述条件时不应为了展示 Agent 而强制联网。

## 6. 联网能力不能只是一个搜索框

V2 将联网研究拆为多个职责清晰的工具，避免“搜索一次后让 LLM 直接推荐”。

### 6.1 Source Search

输入规范化查询、品类、目标字段、地区、时间要求和可选站点白名单。

输出 URL、标题、域名、摘要、来源类型、搜索时间、搜索状态、延迟和费用；不输出“该商品满足硬约束”的最终判断。

### 6.2 Web Extractor

输入经过 URL 安全检查和来源策略允许的页面，输出正文或必要片段、标题、发布日期、抓取时间、内容哈希，以及动态渲染、登录限制和页面变化状态。

搜索结果摘要不能替代 Web Extractor 的正文证据。

### 6.3 Evidence Normalizer

将页面内容映射到 Domain Pack 字段：

```text
product_id
normalized_field
normalized_value
raw_value
unit
region
version
source_id
observed_at / effective_time
evidence_span
confidence
```

LLM 可以提出字段候选，但 Schema 和规则代码决定字段、单位、操作符和数据类型是否有效。

### 6.4 Evidence Check

比较本地证据、联网证据和来源优先级，输出 `matched`、`not_matched`、`unknown` 或 `conflict`。只有 `matched` 且来源满足字段策略的事实，才允许进入本轮完整候选池。

### 6.5 Evidence Promotion

联网证据默认只在当前请求或带 TTL 的临时缓存中使用，不自动写入正式商品库。

```text
联网结果
  → 临时证据区
  → Schema 与实体对齐
  → 来源、许可、版本和时间检查
  → 人工或自动质量门
  → 发布为新 Product Pack/Data Version
```

这样可以避免一次错误搜索永久污染知识库。

## 7. 百炼联网搜索实施方案

### 7.1 第一版复用现有百炼凭据

项目已经使用阿里云百炼，因此第一版不新增 Tavily、Exa 等 API Key。使用现有安全配置层读取 Key，不在代码、文档、日志或测试夹具中写入真实值。

官方资料：

- [大模型如何联网搜索](https://help.aliyun.com/zh/model-studio/web-search/)
- [Responses API 与 web_search/web_extractor](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses)

### 7.2 实现独立 Provider

主 Agent 保持现有 LLM Provider；联网能力单独实现 `BailianWebSearchProvider`，避免把搜索隐藏在主模型回答中。

第一版优先使用能明确返回来源列表和搜索状态的调用路径。OpenAI-compatible Chat 可以保留为兼容路径，但不能只根据模型回答猜测是否执行了搜索。

建议配置：

```text
model = qwen-plus
forced_search = true
search_strategy = turbo
enable_source = true
assigned_site_list = 品牌官方域名白名单
freshness = 仅动态任务按需设置
```

正式参数必须以实施当天官方文档和账户可用模型为准。

### 7.3 后续升级

基础搜索稳定后，再评估支持 `web_search + web_extractor` 的百炼 Responses API 模型。该模型只服务联网工具，不要求同时迁移主 Agent、Embedding 和 Reranker。

### 7.4 成本和限流

- 每次任务设置最大搜索次数、页面数、网页 Token、费用和超时。
- 相同公开稳定查询可使用带 TTL 和数据版本的安全缓存。
- 401/403 不重试；429、5xx 和超时有限重试。
- 必须检查搜索是否真实触发，不能把平台跳过搜索后的模型常识当成搜索结果。
- 价格和限流会变化，批量评测前重新核对官方文档并运行 3～5 条成本 smoke test。

## 8. V2 必须具备的完整能力

### 8.1 Category Router 与 Schema Registry

- 识别品类和任务类型。
- 多品类或品类不明确时主动澄清。
- 根据品类加载对应 Domain Pack。
- 未安装品类进入开放研究模式，不加载其他品类字段猜测。

### 8.2 Domain Pack

| 组成 | 职责 |
|---|---|
| Metadata | 品类 ID、名称、版本、地区和数据版本 |
| Field Schema | 字段类型、单位、动态性、是否允许硬约束 |
| Aliases | 中英文、缩写、口语、否定和取消表达 |
| Constraint Rules | 操作符、单位换算、范围和未知值规则 |
| Source Policy | 来源优先级、站点白名单和有效期 |
| Checker Rules | 硬约束的确定性复核方法 |
| Ranking Profile | 使用场景、软评分维度和可调权重 |
| Eval Fixtures | 正例、困难负例、冲突、过期和故障用例 |

### 8.3 Product Pack

- 支持规范化 CSV/JSON 及来源清单。
- 校验必填字段、单位、型号、地区和许可信息。
- 识别同型号、地区版、配置版和别名。
- 幂等生成 SQLite、事实卡、向量文档和索引 Manifest。
- 使用 staging → validate → publish，失败时保留旧版本。
- 新商品无需修改业务代码。

### 8.4 自然约束理解与澄清

采用“LLM 提取 + 原句 span + Schema 校验 + 规则复核”：

- 支持“三千以内”“27 寸左右”“Type-C 一线通”等表达。
- 支持中英文混合、单位省略、否定、覆盖和取消。
- 区分硬要求、软偏好、用途和背景描述。
- 影响候选集合的歧义必须向用户澄清。
- 未支持字段进入 `unsupported`，不能静默转成硬约束。

### 8.5 有界 Agent Runtime

- 根据任务调用 Product Query、KB Search、Source Search、Web Extractor、Evidence Check、Compatibility Check、Memory 和 Checker。
- 无依赖任务允许并行；有依赖任务按多跳顺序执行。
- 根据候选不足、字段缺失、冲突、过期或工具失败调整路径。
- 限制步骤、工具次数、Token、费用、页面数和超时。
- 达到预算时返回已有证据和未完成项，不无限循环。

### 8.6 多跳检索

一次复杂决策可能包含：

1. 用结构化查询生成完整候选池。
2. 用本地 KB 核验关键稳定字段。
3. 对缺失字段或新型号生成联网查询。
4. 打开官方页面并提取证据。
5. 对冲突字段核对地区、版本、日期和来源优先级。
6. 对设备、接口、协议或配件执行兼容性检查。
7. 把完整候选池交给 Checker 和 Ranker。

上一跳的候选、缺失字段和冲突状态必须真正影响下一跳查询。

### 8.7 Constraint Checker 与 Decision Ranker

**资格层：** Checker 使用结构化数据和已核验证据决定候选是否满足硬条件；LLM 无权添加被淘汰候选。

**排序层：** 只对通过 Checker 的候选，按照品类和用途执行可解释排序。

- 显示器：文本清晰度、游戏、色彩工作、接口和桌面适配。
- 笔记本：便携、续航、开发/创作性能、扩展和噪声。
- 耳机：通勤降噪、通话、佩戴、音质倾向、延迟和兼容性。

报告解释权重、证据覆盖、优势和代价，不能输出没有来源支撑的精确主观分数。

### 8.8 分层记忆

- 会话记忆保存本轮约束、候选、证据状态和工具轨迹。
- 长期记忆只保存用户明确确认的稳定偏好。
- 不保存价格、库存或模型生成的商品事实。
- 偏好分为通用偏好和品类偏好。
- 记忆具备来源、更新时间、版本和失效规则。
- 用户可以查看、修改、删除和关闭。
- 用户和会话之间必须隔离，公开 Demo 不使用共享硬编码用户。

### 8.9 可解释报告与 UI

最终报告至少展示：

- 识别出的硬约束、软偏好和澄清结果。
- 当前运行模式：可信决策或开放研究。
- 推荐候选、适用场景、优势、代价和排序理由。
- 淘汰候选及具体违规字段。
- 来源、地区、版本、观察时间和数据新鲜度。
- 未知字段、来源冲突、过期信息和工具降级。
- 脱敏工具轨迹和本轮 Memory 影响。
- 放宽某项条件后的可选结果。

UI 支持品类切换、约束标签、候选对比、来源抽屉、冲突提示、数据新鲜度和 Memory 管理。

### 8.10 评测、可观测和安全

- 分开评测约束理解、路由、检索、搜索、网页提取、证据核验、Checker、排序、Memory 和 E2E。
- 记录数据版本、Domain Pack 版本、工具路径、延迟、Token、费用、缓存和结果哈希。
- 评测包含新表达、新商品、新品类、相似型号、地区版、冲突、过期、证据不足和工具故障。
- 保留第一次结果和失败案例，修复后使用独立回归。
- 不记录 Key、Authorization、Cookie、私钥、完整 Prompt 或个人敏感信息。

## 9. 目标架构

```text
用户 / WebUI / API
        │
        ▼
需求解析 ── 品类路由 ── 运行模式判断
        │                  │
        │          Schema Registry / Domain Pack
        ▼
有界 Agent Runtime
        ├── Product Query / Text2SQL ── 本地结构化商品库
        ├── KB Search + Reranker ───── 本地稳定资料库
        ├── Source Search ──────────── 网络来源发现
        ├── Web Extractor ──────────── 页面正文与元数据
        ├── Evidence Normalizer ────── 字段、单位、地区和时间
        ├── Evidence Check ─────────── 四态核验与冲突处理
        ├── Compatibility Check ────── 设备/接口/协议关系
        └── Memory ─────────────────── 会话状态与确认偏好
        │
        ▼
完整候选池 + 字段级证据账本
        │
        ├── Constraint Checker ── 决定能否推荐
        └── Decision Ranker ───── 决定合规候选如何排序
        │
        ▼
带来源、时间、淘汰原因、权衡、未知项和降级状态的决策报告

数据治理：
Product Pack → 校验/实体对齐 → SQLite/事实卡/向量索引 → Data Version
联网证据 → 临时证据区 → 质量门 → 可选 Evidence Promotion
```

### 9.1 三类边界

| 通用内核负责 | Domain Pack 负责 | Source Connector 负责 |
|---|---|---|
| Agent 循环、预算、并发、重试和停止 | 品类字段、单位、别名和约束 | 搜索、抓取、限流和来源元数据 |
| 通用工具和证据协议 | 来源优先级和字段有效期 | 页面正文、哈希和观察时间 |
| Checker/Ranker 执行框架 | Checker 规则和场景评分 | 网络错误与降级状态 |
| Memory、报告和可观测 | 品类评测夹具 | 不负责判断候选是否合格 |

### 9.2 编排框架决策

V2 目标架构不预先强制绑定 LangGraph。V1 已有自研有界 ReAct，V2-1 应在通用 `AgentState` 和工具契约确定后完成隔离 PoC，再作决定：

- PoC 通过：LangGraph 只负责 State、Node、条件路由、并行、Checkpoint 和 Interrupt；现有工具、Evidence Check、Memory 和 Constraint Checker 继续保留。
- PoC 未通过：继续使用自研循环，但按相同状态节点和路由契约重构，并用 ADR 记录原因。
- PoC 不得直接替换 V1 主链，也不得为了出现技术名词而降低 V1 回归、可解释性或安全门。

## 10. 分阶段实现路径

每个阶段完成后必须运行测试、更新阶段文档、形成独立提交、推送远端并停止，等待用户确认。不能把计划能力写成已实现能力。

### V2-0：冻结 V1 基线

**目标：** V2 重构不破坏当前作品集。

**任务：**

- 确认 V1 Tag/Release 和稳定 `main`。
- 创建独立 V2 开发分支。
- 冻结现有测试、40 条任务、12 个型号和历史结果。
- 记录显示器硬编码、重复逻辑和外部依赖。
- 禁止覆盖 V1 历史评测文件。

**验收：** 干净克隆继续通过 V1 离线测试和四个 Demo；工作区干净；V2 分支和迁移清单完成。

### V2-1：通用契约与 Monitor Domain Pack

**目标：** 解除字段、规则和工具与显示器的直接绑定。

**任务：**

- 建立 Product、Field、Constraint、Evidence、Source、Candidate 契约。
- 实现 Schema Registry 和 Domain Pack Loader。
- 把显示器字段、别名、来源策略和 Checker 规则迁入 Monitor Pack。
- Text2SQL 白名单、Evidence Check 和报告字段从 Pack 生成。
- 删除或收敛未进入主链的重复约束解析。

**验收：** V1 回归全部通过；通用内核不出现显示器专属字段；结果无非预期变化。

### V2-2：Product Pack 与证据账本

**目标：** 让新增商品成为数据操作，并为联网证据建立统一落点。

**任务：**

- 定义 Product Pack 和 Evidence Record Schema。
- 实现单位规范化、实体对齐、来源、地区、版本和时间校验。
- 幂等生成 SQLite、事实卡、向量文档和 Manifest。
- 实现 staging → validate → publish 和失败回滚。
- 建立当前请求临时证据区和数据版本标识。

**验收：** 不改业务代码导入第 13 个显示器；错误 Pack 不污染当前版本；重复构建结果一致。

### V2-3：受控 Source Search MVP

**目标：** 把当前 unavailable Web 工具替换为真实、显式、可审计的搜索工具。

**任务：**

- 实现 `BailianWebSearchProvider` 和统一 Source Search Tool。
- 优先使用现有百炼 Key 和可返回来源的调用路径。
- 先支持 Dell、ASUS、LG、BenQ 等官方域名白名单。
- 记录触发原因、搜索状态、来源列表、延迟和成本。
- 加入步骤、费用、RPS、重试和缓存限制。

**验收：** 固定官方规格查询可以真实返回来源；强制搜索能检测是否发生；401/403、429、超时和无结果按契约降级；密钥扫描为 0。

### V2-4：网页提取与开放研究模式

**目标：** 让本地不存在的新商品形成可追溯研究结果，而不是只得到搜索摘要。

**任务：**

- 实现 URL 安全、来源策略和 Web Extractor。
- 保存必要片段、页面元数据、抓取时间和内容哈希。
- 实现 Evidence Normalizer 与临时证据生命周期。
- 接入 Evidence Check，搜索摘要禁止直接进入 Checker。
- 在 API、UI 和报告中标明 Trusted/Open 模式。

**验收：** 至少一个数据库外显示器能形成带来源、时间、未知字段和待核验项的报告；断网时本地主链不受影响。

### V2-5：自然约束理解与主动澄清

**目标：** 支持真实用户表达，而不是只匹配固定词表。

**任务：**

- LLM 输出带原句 span 的类型化 Constraint Proposal。
- Schema/规则校验字段、单位、范围、否定、覆盖和取消。
- 支持中文数字、同义表达、模糊范围和中英文混合。
- 实现歧义评分和澄清状态机。

**验收：** 未见表达集达到目标；歧义条件不静默进入 Checker；会话中可以覆盖和取消旧条件。

### V2-6：Laptop Domain Pack

**目标：** 用第二个复杂品类证明通用化。

**任务：**

- 定义 CPU、GPU、内存、存储、重量、续航、屏幕、接口和可升级性。
- 治理一组可公开复现的笔记本商品和来源。
- 实现办公、开发、创作和游戏场景规则。
- 增加配置版、地区版和相似型号困难用例。

**验收：** 笔记本复用相同内核和工具协议；新增品类不修改通用内核；两个品类均有冻结评测。

### V2-7：Decision Ranker 与 Memory 升级

**目标：** 从条件筛选升级为可解释的个性化决策。

**任务：**

- 为 Domain Pack 定义用途评分维度和透明权重。
- 只对 Checker 合规候选排序。
- 支持偏好调整和 what-if 对比。
- 长期偏好分层、版本化、可失效并按用户隔离。

**验收：** 改变用途只改变合规候选顺序，不改变资格；报告解释排序变化；删除 Memory 后不再影响请求。

### V2-8：Headphone Domain Pack 与跨品类评测

**目标：** 验证主观证据、兼容性和跨品类隔离。

**任务：**

- 定义佩戴、连接、编码、降噪、通话、续航、重量和延迟。
- 区分官方规格、专业实测和主观评价的权限。
- 建立通勤、会议、游戏和音乐场景规则。
- 建立三品类统一评测和交叉污染测试。

**验收：** 三个 Domain Pack 共用内核；主观证据只影响排序；不同品类字段和 Memory 不互相污染。

### V2-9：产品 UI、完整评测与作品集发布

**目标：** 形成五分钟可理解、可操作、可复现的 V2 作品集。

**任务：**

- UI 展示品类、约束、候选、来源、冲突、模式、时效和 Memory。
- 准备本地可信、新商品研究、动态信息、冲突处理和连续追问 Demo。
- 运行跨品类消融、故障、成本、延迟和稳定性评测。
- 完成 Windows 干净克隆和离线回放。
- 精简 README，只呈现真实能力、指标、Demo 和限制。

**验收：** 三品类 Demo 和开放研究 Demo 通过；首次结果和失败保留；无密钥或运行产物；公开说明不夸大市场覆盖和生产 SLA。

## 11. V2 发布门槛

以下均为**目标，不是当前成绩**。数据冻结后可以校准，但不能在看到结果后随意降低或只报告最好一次。

### 11.1 必须通过的安全与工程门

| 指标 | 目标 |
|---|---:|
| 可信模式下违规候选进入推荐 | 0 |
| Checker 故障 fail closed | 100% |
| 搜索摘要直接作为硬事实 | 0 |
| 动态事实带来源、地区和观察时间 | 100% |
| 开放研究结果伪装为治理结论 | 0 |
| 歧义条件未经确认进入硬约束 | 0 |
| 新商品导入需要修改业务代码 | 0 |
| Product Pack 重复构建 | 幂等 |
| 用户/会话 Memory 交叉污染 | 0 |
| 真实凭据进入代码、文档或日志 | 0 |
| V1 既有离线回归 | 全部通过 |

### 11.2 建议质量目标

| 能力 | 目标 |
|---|---:|
| 已验证品类 | 3 个：显示器、笔记本、耳机 |
| 治理商品 | 每品类至少 12 个，建议 12～20 个 |
| 跨品类冻结任务 | 至少 90 条，每品类不少于 30 条 |
| 联网专项任务 | 至少 15 条，覆盖新商品、动态、冲突和失败 |

| 每品类可信模式 E2E 正确率 | 不低于 80% |
| 证据不足/困难负例拒答率 | 不低于 90% |
| 强制联网任务真实搜索检测 | 100% |
| 静态充分证据任务避免无效联网 | 不低于 95% |

所有指标必须报告分母，并分开首轮、修复后回归、回归集和 holdout。

## 12. 最终必须展示的五个场景

### 场景一：本地可信筛选

用户提出明确预算、尺寸和接口要求；Agent 使用 SQL、KB、Evidence 和 Checker 完成可复现推荐，不调用网络。

### 场景二：数据库外新商品

用户询问一个本地没有的新型号；Agent 发现未知商品，搜索品牌官网、提取字段，输出开放研究报告和待确认项。

### 场景三：当前价格或库存

Agent 识别动态任务，查询允许的动态来源，所有价格带地区和观察时间；来源不可用时明确降级。

### 场景四：来源冲突

本地资料与网页对同一字段不一致；Agent 根据地区、版本、时间和来源等级保留冲突，不让 LLM 静默选一个答案。

### 场景五：连续追问与偏好变化

用户在多轮对话中增加、覆盖或取消条件；Agent 复用会话状态和确认偏好，重新筛选并解释候选变化。

## 13. 优先级

### P0：让项目真正不再固定

1. 冻结 V1。
2. Domain Pack 与通用契约。
3. Product Pack 与证据账本。
4. 真实 Source Search。
5. Web Extractor 与开放研究模式。

完成 P0 后，ProofPick 才从静态显示器 Demo 升级为“可以发现和研究新商品”的 Agent。

### P1：证明通用性和自然交互

1. 自然约束理解与澄清。
2. Laptop Domain Pack。
3. Decision Ranker 与 Memory 升级。

### P2：完成跨品类验证与展示

1. Headphone Domain Pack。
2. 跨品类评测。
3. UI、Windows 复现和作品集发布。

### 暂不优先

- GraphRAG/Neo4j：只有兼容性多实体关系成为可测瓶颈后再评估。
- 自动下单、支付、抢购和电商账户操作。
- 大规模全网爬虫、登录后内容和绕过网站限制。
- 公网多租户和生产 SLA。
- 为增加模型数量而引入无差异 Provider。
- 在通用 Schema 和联网证据链未稳定前扩展大量品类。

联网搜索当前的优先级高于 GraphRAG，因为项目首先缺少的是商品覆盖和数据时效，而不是更复杂的图推理。

## 14. 主要风险与控制

| 风险 | 后果 | 控制策略 |
|---|---|---|
| 搜索摘要错误 | 无依据规格进入推荐 | 必须打开页面、提取证据并经过 Evidence Check |
| 搜索未真实触发 | 把模型常识误认为联网结果 | 强制检测 `search_info`/工具事件，无证据即降级 |
| 网页变化或不可访问 | Demo 不稳定 | 官方域名优先、缓存快照、离线回放、本地主链独立 |
| 动态价格过期 | 推荐基于旧价格 | 地区、`observed_at`、TTL 和过期提示 |
| 联网证据污染正式库 | 一次错误长期生效 | 临时证据区和 Evidence Promotion 质量门 |
| 抽象过度 | 框架复杂但没有真实收益 | 先迁移显示器，再用笔记本和耳机验证 |
| 多品类复制硬编码 | 三个互不兼容的 Agent | 品类差异必须进入 Domain Pack |
| LLM 错误解析条件 | 错筛或违规推荐 | span、Schema、规则、澄清和 Checker 多层隔离 |
| 主观评分伪精确 | 推荐依据无法解释 | 权重透明、证据覆盖、允许用户调整、不宣称客观最优 |
| 评测泄漏 | 指标不能反映泛化 | 冻结 holdout、新表达、新商品和首次结果保留 |
| V2 破坏 V1 | 失去当前作品集 | 独立分支、Release、兼容层和阶段全量回归 |

## 15. Non-goals 与表述边界

V2 不做：

- 自动下单、支付、返利、抢购和账户操作。
- 未经许可的大规模网页抓取或受限内容存储。
- 把模型生成内容当成商品事实源。
- 在没有数据和评测时宣称支持全部电子产品。
- 生产级并发、SLA、安全沙箱或公网多租户承诺。

V2 完成前，准确表述为：

> ProofPick 是一个以显示器为已验证场景、采用本地可信检索和确定性安全门，并计划扩展受控联网研究与多品类 Domain Pack 的消费决策 Agent 原型。

V2 完成后，允许表述为：

> ProofPick 是一个面向多品类电子产品的可扩展决策 Agent，通过本地治理数据与受控联网研究完成候选筛选、多跳核验、动态信息补充和确定性约束复核。

即使 V2 完成，也不能表述为“覆盖全部市售商品”“实时价格绝对准确”或“生产零错误”。

## 16. V2 完成定义

- [ ] 显示器、笔记本、耳机三个 Domain Pack 共用同一内核。
- [ ] 新商品可通过 Product Pack 导入，无需修改业务代码。
- [ ] 新品类主要通过 Domain Pack 接入，不复制 Agent 主流程。
- [ ] 数据库外新商品可进入开放研究模式并获得带来源报告。
- [ ] 至少一个真实 Source Search 和一个 Web Extractor 可用。
- [ ] 搜索结果经过字段规范化、证据核验和临时证据治理。
- [ ] 动态事实带来源、地区、时间和过期策略。
- [ ] 多跳路径会根据候选、缺失字段和冲突继续查询。
- [ ] 可信模式最终候选全部经过确定性 Checker。
- [ ] 软偏好排序可解释且不能改变硬约束资格。
- [ ] Memory 可查看、修改、删除、关闭、失效并按用户隔离。
- [ ] 跨品类、联网、故障、成本和稳定性评测可复核。
- [ ] Windows 干净克隆可以构建、启动、演示和停止。
- [ ] README、Demo 和简历只描述真实完成的能力。
